# Multi-Agent Rooms Protocol Specification

This document details the core message schema, persistence format, and conceptual automation rules for the Multi-Agent Rooms project. This specification is designed to facilitate deterministic code generation and clear communication between agents and the human operator.

---

### **1. Core Message Schema**

This defines the structure of messages exchanged within the room.

```typescript
interface RoomMessage {
  /** A unique UUID for the message, generated on creation. */
  id: string;

  /** The timestamp of message creation in ISO 8601 format (e.g., "2025-11-15T12:00:00Z"). */
  timestamp: string;

  /** The type of message being sent. */
  type: 'agent_output' | 'agent_prompt' | 'human_prompt' | 'system_notification';

  /** The originating agent or user. */
  source: 'PeterB' | 'Codex' | 'Claude' | 'Gemini' | 'System';

  /** The intended recipient. Can be a specific agent or 'all' for broadcast. */
  target: 'PeterB' | 'Codex' | 'Claude' | 'Gemini' | 'all';

  /** The main content of the message. */
  body: string;

  /** An optional object for additional, non-essential information. */
  metadata?: {
    /** If forwarded, the ID of the original message. */
    original_message_id?: string;
    /** Any other relevant context, e.g., file paths, line numbers, tool calls. */
    [key: string]: any;
  };
}
```

#### **Message Types:**
*   `agent_output`: Output generated by an AI agent (e.g., code, analysis, tool results).
*   `agent_prompt`: A message intended as a prompt for another AI agent.
*   `human_prompt`: A direct instruction or query from the human operator (PeterB).
*   `system_notification`: Messages from the 'System' source, indicating events like agent status changes, errors, or room state updates.

#### **Source/Target Identifiers:**
These correspond to the named participants in the room. 'System' is reserved for internal framework messages. 'all' is a special target for broadcast messages.

### **2. Persistence Format**

Messages will be persisted in a **line-delimited JSON (JSONL)** format. Each line in the transcript file is a complete, self-contained `RoomMessage` object.

**Example `transcript.jsonl`:**
```json
{"id":"uuid-1","timestamp":"2025-11-15T12:00:00Z","type":"human_prompt","source":"PeterB","target":"Codex","body":"Draft the Bun server skeleton."}
{"id":"uuid-2","timestamp":"2025-11-15T12:00:05Z","type":"agent_output","source":"Codex","target":"PeterB","body":"// rooms/server.js\nimport { serve } from 'bun';...","metadata":{}}
{"id":"uuid-3","timestamp":"2025-11-15T12:00:10Z","type":"agent_prompt","source":"PeterB","target":"Claude","body":"Here is the server code from Codex. Please build the UI.","metadata":{"original_message_id":"uuid-2"}}
```

**Advantages of JSONL:**
*   **Append-Only:** Highly efficient for writing new messages to the end of the file, suitable for real-time logging.
*   **Resilient:** A malformed line (due to corruption or partial write) does not prevent parsing of other messages.
*   **Streamable:** Can be read and parsed line-by-line without loading the entire file into memory, ideal for large transcripts.
*   **Human-Readable:** Easily inspectable with standard text editors.

### **3. Automation Rules Data Structure (Conceptual)**

To support UI-managed automation (e.g., automatically forwarding certain messages), the Bun Hub could maintain a list of rule objects.

```typescript
interface AutomationRule {
  /** A unique identifier for the rule. */
  id: string;
  /** A human-readable name for the rule (e.g., "Auto-forward Claude's code to Gemini"). */
  name: string;
  /** The source agent whose messages this rule applies to. */
  source: 'Codex' | 'Claude' | 'Gemini';
  /** The target agent to which messages matching this rule should be forwarded. */
  target: 'Codex' | 'Claude' | 'Gemini';
  /** Optional: A regular expression to filter message bodies. Only messages matching this regex will trigger the rule. */
  body_filter_regex?: string;
  /** Whether the rule is currently active. */
  enabled: boolean;
}
```

## Implementation Guide

The following sections describe the actual implementation of the Multi-Agent Rooms system, including setup, usage, and architecture details.

### Architecture


### Components

#### 1. Server (`server.js`)
WebSocket hub that coordinates agents:
- Accepts WebSocket connections from agents and web UI
- Routes messages between agents with human approval
- Maintains message history
- Broadcasts to web UI dashboard

#### 2. Web UI (`client.html`)
Dynamic multi-pane dashboard showing:
- One pane per connected agent (Claude, Gemini, Codex, etc.)
- Panes are created/removed dynamically as agents join/leave
- **Bottom**: Controls to forward messages and inject prompts

#### 3. Agent Bridge (`agent-bridge.js`)
Adapts CLI tools to WebSocket:
- Wraps `claude`, `gemini`, or other CLI tools
- Captures stdout/stderr → sends to room
- Receives messages from room → forwards to agent's stdin

```bash
bun packages/rooms/agent-bridge.js \
  --name gemini \
  --command "gemini --approval-mode auto_edit --resume latest"
```

**Terminal 3 - Codex:**
```bash
bun packages/rooms/agent-bridge.js \
  --name codex \
  --command "codex --interactive"
```

### Usage

#### View Agent Output
- Each agent's output appears in its respective pane
- System messages (joins/leaves) appear in all panes
- Human messages appear highlighted in all panes

#### Forward Messages Between Agents
1. Click a message in any pane to select it
2. Choose target agent from dropdown
3. Click "Forward Selected →"
4. Message is sent to target agent's stdin

#### Inject Your Own Messages
1. Type message in text area at bottom
2. Click "Send" or press Cmd/Ctrl+Enter
3. Message appears in all panes for context

#### Export Transcript
Click "Export Transcript" to download full conversation history as text file

### How It Works

#### Message Flow

1. **Agent → Room:**
   - Agent produces output on stdout
   - Bridge captures and sends to WebSocket server
   - Server broadcasts to web UI
   - Appears in agent's pane

2. **Room → Agent:**
   - User selects message and clicks "Forward"
   - Server sends to target agent's bridge
   - Bridge writes to agent's stdin
   - Agent processes as if user typed it

3. **Human → Room:**
   - User types message and clicks "Send"
   - Server broadcasts to all agents
   - Appears in all panes for context
   - Does NOT auto-forward to agents (prevents spam)

#### Message Types (Implementation)

- `agent_output` - Agent produced output
- `agent_input` - Forwarded to agent's stdin
- `human_message` - PeterB injected message
- `system` - Server status (joins, leaves)
- `history` - Full message history (on web UI connect)

### Limitations

#### Current Version
- ✅ Real-time message display
- ✅ Manual message forwarding
- ✅ Human message injection
- ✅ Transcript export
- ❌ No automatic routing rules
- ❌ No message queuing/threading
- ❌ No authentication (local use only)
- ❌ No persistence across restarts

#### Agent Compatibility
Works with any CLI tool that:
- Reads from stdin
- Writes to stdout
- Runs in interactive mode

**Confirmed working:**
- ✅ `claude` (Claude Code CLI)
- ✅ `gemini` (Google Gemini CLI)
- ⚠️ Custom wrappers (YMMV)

**Not compatible:**
- ❌ GUI applications
- ❌ Non-interactive scripts
- ❌ Tools that require terminal control codes

### Troubleshooting

#### Agent won't connect
```bash
# Check if server is running
curl http://localhost:8765

# Check WebSocket connection
bun packages/rooms/agent-bridge.js --name test --command "echo 'hello'"
```

#### Messages not appearing
- Check agent stdout is not buffered (use `--unbuffered` if available)
- Verify agent is actually producing output
- Check browser console for errors

#### Agent stopped responding
- Agent process may have exited (bridge will restart after 3s)
- Check terminal for error messages
- Try killing and restarting the bridge

#### Web UI shows "Disconnected"
- Server may have crashed
- Check server terminal for errors
- Restart server: `bun packages/rooms/server.js`
