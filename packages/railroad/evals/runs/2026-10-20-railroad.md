1. **The harness, not a skill: `bunfig.toml` cannot be written with Write/Edit.** `scripts/evals.ts` runs `claude -p … --permission-mode acceptEdits`, and Claude Code treats `bunfig.toml` as a sensitive file. railroad #3's Write was refused, so its 3 tests "fail" under a bare `bun test` and pass under its `bun run test`. railroad #1 got past the check by writing the file through Bash. Either allow the file for these sessions, or have the harness run the project's `test` script when there is one. `railroad/reference/testing.md:4` is right as written.
2. **The harness, not a skill: an empty start installs npm's packages.** bun-route #1 followed SKILL.md §1, `bun add @blueshed/railroad`, and got the registry's 0.17.0, which differs from the checkout's (flat files, different `signals.ts`/`jsx.ts`/skill pages). That breaks the "never npm's" promise in `scripts/evals.ts:7`. The harness needs a way to resolve `@blueshed/*` to the checkout in an empty start, for example a project or global `bunfig.toml` install scope, or a relink after the session that is then re-graded.
3. **`bun-route/SKILL.md` §1 against `reference/tsconfig.md:27` and §4.** §1 says to install "nothing for js/ts". `tsconfig.md:27` and §4 say `types: ["bun"]` needs `@types/bun`. bun-route #2 followed §1 and the query, so `bun check` still fails. bun-route #3 followed `tsconfig.md`. §1 should say that ts and tsx modes always need `bun add -d @types/bun`, and §1 (detecting the mode) should treat a missing `@types/bun` beside `types: ["bun"]` as something to fix in an existing project too.
4. **No page names `bun check` as the type check** (`railroad/SKILL.md` "Order of work" step 5 and `reference/setup.md`; `bun-route/SKILL.md` §5). railroad #3 and bun-route #3 ran `bunx tsc`, which downloads TypeScript. railroad #2 skipped the check: "doesn't have TypeScript installed". Only bun-route #1 had bun init's CLAUDE.md telling it to use `bun check`. §5 "Verify" should start with `bun check`, and the railroad skill should say the same once.
5. **`bun-route/reference/templates.md`'s js/ts snippet makes a global script.** A client `.ts` with no `import` or `export` puts its top-level `const`s in the global scope, so names lib.dom already declares (`name`, `status`, `top`, `parent`, `length`…) fail `bun check`. bun-route #2's own `contact/contact.ts:15` (`status`) has this bug, and so does the `greeting` fixture's `main.ts:2` (`name`). The snippet should start with `export {};`, or the page should say why it is needed.
6. **`railroad/reference/realtime.md`** (and `signals.md:52`) still do not give the cost: a read after a change is a shallow copy of the row references, and `put` finds a known key by `indexOf`. railroad #1 went to `src/signals.ts` for it, as in round 1. Under a query that says "thousands … must not clone the whole list", one sentence would save the trip. This also shows that a linked checkout exposes `src/`, `examples/` and `evals/` (the expected lines) in `node_modules`. No session read `evals/`, but the answer key is one `ls` away (finding 2's fix should close this too).
7. **`bun-route/reference/webview.md`** (round 1, findings 5-7, unchanged):
   - (a) it does not say what to do in an app without railroad: `bun add -d @blueshed/railroad` for the kit, or raw `Bun.WebView` with `webview-recipes.md`'s `waitFor`;
   - (b) its skeleton's top-level `await startServer` contradicts bun-route #3's `beforeAll` line;
   - (c) "Always type `evaluate<string>(…)`" is missed for calls whose result is thrown away (railroad #2).
8. **Servers outlive the sessions** (`bun-route/SKILL.md` §5). bun-route #1 and #2 stopped theirs with `pkill -f "bun server.ts"`, which kills any run's server. railroad #3's `cmd & … kill %1` left pid 65289 listening on :3917, still running now. Four of the six sessions picked the same port, 3917, while running four at a time, so a curl could reach another run's server. §5 should say: start on `PORT=0` or a random port, keep the pid (`$!`), and kill that pid alone. Or it should prefer the `startServer({ port: 0 })` factory, which bun-route #3 and railroad #2 used.
9. **The scenarios and fixtures:**
   - `fixtures/plain` and `fixtures/greeting` both fail `bun check` before any session starts: `types: ["bun"]` with no `@types/bun`, and the harness runs no `bun install` after `copy`. `greeting/main.ts:2`'s `const name` also clashes with lib.dom. Give each fixture `devDependencies: { "@types/bun": … }` and an install, and make `main.ts` a module (`export {};`) with a name that does not clash. Then a failing check in these runs means the session.
   - bun-route #2's line 4 names the import `contactPage`; it should accept any name.
   - railroad #3's line 5 should say that a handler returning a component that returns `when(resolved(…))` counts.
   - bun-route #3's lines 2 and 3 contradict `webview.md` (finding 7a, b). Either the page changes, or the lines accept a top-level start and raw `Bun.WebView` in an app without railroad.
   - `results.json` reports `bun test` exit 1 for "0 test files" (bun-route #1, #2). The harness could record that as no tests.
