## The two must-nots run 3 left at "partly"

- **Stage 4, the kit lent as a whole: passes.** The strimmer's battery and charger are parts under
  the strimmer, never on the list alone, so borrowing the strimmer lends all three and returning it
  returns them; a loan made before it became a kit shows all three. But the parts are kept inside
  the tool in `shed.json`, not as rows under it, because the tools never left the JSON file (below).
  Nothing on the server checks a loan's tool is on the list at all (the app's todo 3), so a hand-made
  write could still lend anything; the page offers only whole tools.
- **Stage 4, the due date: fails**, a must-not run 3 passed. The session chose to work the due date
  out (`dueOf`, two weeks from the loan's day, in `borrowing.ts`, the page's module) and said so:
  "it isn't stored ... no backfill that could give them the wrong date". That is `expected.md`'s
  "no due date computed in the page in place of being stored", and the app's todo 11 already finds
  the cost: a loan can't be given longer.
- **Stage 5, who may see what: partly, better than run 3.** Three of four are paths: one's own
  (`owns: "@id"`), Sam's board (`people[keeper=true].id`), the committee's
  (`people[committee=true].id`, which now holds every loan and the phone numbers). A field's loans
  are a recompute document with a function, `owns: (me, name) => me.fields.includes(...)`, the shape
  delta-doc's ownership page names as "the sign they hang in the wrong place". The session's reason:
  "a person has no field of their own (Sam and Cara have no plot), so the field gathers them". Run 3
  wrote functions for all of them.
- **Stage 5, hand-written SQL: partly.** The schema is compiled (`generateSql`, applied at start),
  but the message and the shed's list are kept whole as JSON in a `kept_docs` table the app makes
  itself, with a 94-line writer (`src/resources/kept.ts`) calling delta's internals
  (`_delta_bump_and_notify`, `mintIds`, `normalizeForBroadcast`) so both sheds hear a change.

## Findings

1. **A due date worked out in the page (the skills).** delta-doc's schema page and evolve's SQLite
   page say "a fact from other rows is worked out, never stored". The session applied it to a value
   from the row's own day and a rule, which a person later changes (an extension). The rule needs its
   limit: a value someone may change, or a rule that may change, is stored, and a migration fills it
   for the rows before.
2. **The tools stay JSON to the end (the evolve skill, dzql).** Run 3's fix (todo #33) did not take:
   the list stayed `shed.json` through stage 3, the kit's parts went inside it in stage 4, and in
   stage 5 the app wrote its own JSON-in-Postgres store over delta's internals. While the tools are
   JSON, a part cannot be a row and a loan's tool cannot be checked. The step to SQLite in stage 3 is
   where they should have gone: evolve could say so where the step is taken (a document whose rows
   another document names moves with it), and the dzql page could say a JSON document becomes rows,
   never a table of JSON.
3. **A group with people outside it (the skills).** Ownership's group shape puts members under the
   group. Here some people (the keeper, the committee) have no field, so the session left people at
   the root, plots under fields with a bare `person` integer, and fell back to a function. The page
   could show a membership row as its own table between the two (plots: a field and a person), and
   the path through it, for when not everyone is in a group.
4. **Stage 3's session wrote `todo.jsonl` with a Python script**, against the app's CLAUDE.md. Small,
   but the lineage is Bun-only; the template could say why.

Not friction: stages 3 and 4 ended by asking "Want me to commit?", which the driver does.
