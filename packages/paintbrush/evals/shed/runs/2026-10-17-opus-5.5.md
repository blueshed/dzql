## Stage by stage

1. **The shed's list.** One shared document from the start, rows by id, a nameless tool refused
   with a 400. It ledgered that anyone, not only Sam, can change the list, and that two tools can
   share a name (todo 2).
2. **Borrowing.** A document per member (`member:ann`), the basket holding tool ids so a rename
   shows, the loan dated by the server. Passes in full.
3. **What is out.** SQLite, documents over shared rows, Sam's board over every loan, undo by the
   ledger. **Fails a must-not:** "out" is a stored flag on the tool, set by the borrow, not worked
   out from the open loans (finding 1). **Partly:** undo is per page, not per person (todo 9).
4. **Kits and due dates.** Due dates and the kit declared, two migrations, a test from a database
   holding older loans. **Partly:** a kit's parts are tools linked by a `kit` column, not rows under
   the strimmer, and a loan's tools are a JSON column, not rows (finding 4). The kit migration
   finds the strimmer by name (todo 12) and writes `_delta_sequences` by hand (finding 5).
5. **Two sheds.** dzql on Postgres (`DATABASE_URL`), PGlite otherwise; two servers on one database
   behind an advisory lock at set-up; `generateSql` at start; the north shed's `shed.db` carried
   across once. Committed to a branch `two-sheds`; `main` was fast-forwarded to it afterwards.
   **Partly:** who may open what is one function, `mayHave`, matching names, not `owns` paths
   (finding 3); a field's loans come from a `field` column copied onto each loan (todo 15), not a
   path through membership; one-loan-at-a-time is a hand-written trigger outside the migrations
   (finding 2); the tests run both sheds on PGlite in one process (todo 19).

## Findings

Each says where the change belongs.

1. **A fact from another parent's rows (delta, open as delta #79).** Same as run 1's finding 1: a
   tool's list can't show its open loans, so "out" and "due" are stored on the tool and written with
   the loan. Two runs have now hit it the same way. Until delta can derive it, the evolve skill
   should say how to keep such a fact honest.
2. **No unique constraint in the schema (delta, open as delta #81).** Run 1 wrote a unique index;
   run 2 wrote a plpgsql trigger with an advisory lock, applied from `shed-api.ts` at every start,
   outside the migration history. Same gap, a heavier workaround.
3. **`owns` as a path is never shown (paintbrush, the evolve skill).** delta 1.2.0 and dzql 0.13.0
   have it, but the evolve skill has no example of an `owns` path, so stage 5 wrote a function over
   document names. The membership case (a field's members see the field's loans) is exactly what a
   path is for.
4. **Lines and parts as rows (paintbrush, the evolve skill).** A loan's tools and a kit's parts
   became JSON and a link column. `expected.md` wants rows under their parent. Nothing in the skill
   shows a one-to-many line table; both runs avoided one.
5. **A migration can't add rows that take the next id (delta).** Migration 003's `up` reads and
   writes delta's internal `_delta_sequences` to give the battery and charger ids. Either `up` gets
   a way to insert through delta, or the sequence table becomes a documented contract.
6. **A replace was a delete then an insert on Postgres (dzql, fixed in #43, unreleased).** Stage 5's
   guard on UPDATE never fired; that is why its trigger is `BEFORE INSERT`. dzql #43 makes a replace
   on a table without versions an update in place. Not released, so the Shed still runs on 0.13.0.
7. **Stories and tests drift apart (paintbrush).** Of the app's 31 stories, 23 have no test with that
   exact sentence: renamed in later stages, punctuation changed, and the template's own four message
   stories never named. `stories.md` is prose nothing checks. Proposed: `stories.ts` exporting the
   sentences, `test(shed.addsTool, …)`, and one test failing on a story no test uses.
