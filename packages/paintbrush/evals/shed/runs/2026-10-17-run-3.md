## Findings

1. **`owns` as a path is still not reached for (dzql, the skills).** The skills now show a path
   through memberships, and stage 5 still wrote functions on names. The path is what dzql compiles
   into reads and RLS; a function is not. Next: an `owns` path in the evolve skill's Postgres page
   as the way, with a function named the exception, and `expected.md`'s check said there.
2. **A kit is held together by the page (delta).** Nothing in the schema can say "these rows go
   with that one" for a write; the session kept parts as rows but lent them from the page. A parent
   chain (parts under their tool) and a write through the tool's document would hold it.
3. **The tools stay a JSON document until Postgres (the evolve skill).** Stage 3 moved loans to
   SQLite and left the tools in `shed.json` ("it turned out unnecessary"); stage 5 then had to
   renumber every tool. The skill could say: when documents share rows, the rows they share move
   together.
4. **An admin write has no delta way in (delta's CLI).** Roles and fields are `UPDATE people` from
   a command, since `delta` has no "write as the server" command for a SQLite file or a database.
   `delta link` exists for sign-in; a `delta write <database> <doc> <ops>` would keep it in delta.
5. **A refusal's words (dzql).** A unique violation on Postgres reaches the page as the database's
   message, where SQLite's answer was a 409 the app could word (app todo 10). dzql could answer a
   unique violation as delta's 409.
6. **One process owns PGlite (dzql, documented).** `bun run link`, `role` and `field` need the dev
   server stopped (app todo 11). Known and said in the docs; the session found it the hard way.

Undo by page, not person, after a reload (app todo 7) is run 2's todo 9 again: delta's cursor is
the page's connection over the socket.
