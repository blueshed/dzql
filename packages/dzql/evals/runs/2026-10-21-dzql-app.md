## Findings

1. **Pages: `reference/bento.md` (*Undo follows the role*) and `reference/scope.md` (*Today's, or
   one shift's*). The pages now carry the eval's answer.**
   - bento.md's example is a front desk's `surfaces.ts`: the receptionist writes, the team reads.
     scope.md's example is "a front desk's visitors", as `desk:2026-10-20`.
   - Scenario 1 copied both verbatim. With the bento example came `undo: true`, which the query
     did not ask for, against SKILL step 5 ("Undo and Redo only when asked") and "Build nothing no
     story needs". That in turn left scenario 3 little to build.
   - Neither example comes from a shipped example: scope.md's `Working:` says "Today's, by date
     or as a root row, none yet".
   - Fix: draw both examples from another domain, or better, from an example that runs them (a
     cafe shift for today's; for Undo by role, an example where only some write: all five examples
     have one bento with `undo: true`, so none shows it yet), so the `Working:` line names it.
   - Eval file: give scenario 1 a line "builds no Undo: none was asked". Or start scenario 3 from
     a fixture with the desk and no Undo, so its line 2 is built rather than found.
2. **Page: SKILL step 1 and `reference/stories.md` (*Watch it fail on its own terms*). Say what
   "the least that loads" is for a cast that signs in. Also an API item for Peter.**
   - Scenario 1 wrote everything before its first run.
   - Its first red was the sign-in route not wired (`405` on `/in/:token`): the stories' `signIn`
     posts there, and the page does not list the route among what to make first.
   - Its second red was the harness crashing: `TypeError: undefined is not an object (evaluating
     'owner.permit')` in `hiddenVerbs`, `src/modelling/harness.ts:1196`, `r.byDocType.get(docType)!`.
     This happens when a story writes a document type that no listed resource owns.
   - Page: list the first things to make in order: `links.ts`, its route in `routes.ts`, and an
     empty resource for each document the stories write.
   - API, an item for Peter: the harness should fail that story in its own words ("no resource
     for desk") rather than crash. This is an API trap the page now has to talk around.
3. **Page: `reference/stories.md` (*Undo, in the stories*). Say that "another's Undo never reaches
   mine" is the kernel's, and needs no story.**
   - The page says "where writes only add rows, nobody's change can be in the way: say so, and
     write no such story". Scenario 3 did not say so, and wrote `tomCannotUndoRaes`, which it
     could not make fail from the app.
   - To learn why Tom's undo is refused, it read `rendering/resources/ledger.ts`.
   - Add one line: the cursor is the session, so a person's undo has only their own writes to
     walk. That another's Undo never takes yours is the kernel's rule, proved by dzql. In an app,
     show it at most with a server test of two sessions, which is what this session did.
4. **Pages: `reference/refusal.md` and `reference/stories.md`. A rule's refusal is a story.**
   Scenario 1 built `refuse("A visitor needs a name.")` in `shape` with no `cannot` story to carry
   it. The words are checked only in a server test. SKILL says "A refusal is a story too", and
   refusal.md's first bullet does say that the story of a rule a control sent says its words
   (`told`). But that is the bullet's last clause, after the `permit` case it leads with. Make it
   a bullet of its own: every `refuse(words)` has its `cannot` story with `told: words`, told from
   the control that sends it (`from: "?new"`).
5. **Page: `reference/where-an-app-lives.md`, or SKILL's "Beyond the cafe". Only the cafe ships.**
   Scenario 2 tried to diff against `node_modules/dzql/examples/leave/`, which is not in the
   package. Say that only `examples/cafe/` is in `node_modules/dzql`, and that the rest are on
   GitHub, as each page's `Working:` links them.
6. **Page: `reference/tests.md`. Name the socket helpers.** Scenario 1 read `test-socket.ts` to
   learn `open(server, cookie)` with `sessions.start({...}).cookie`, and `nextMessage`. Scenario 3
   reused them. tests.md names only `write` and `expectMessage`. One line showing a server test
   opening two signed-in sessions would save the read.

No scenario line is wrong. Two only need tightening, both under finding 1: scenario 1 should say
no Undo was asked for, and scenario 3's line 2 is met by the state it starts from.
