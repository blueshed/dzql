## Findings

1. **A test cannot close a SQLite database and still stay the same on both backends.** The
   recipe's test calls `await roomApi(ws, dir)` and never closes what it opened, and `backends.md`'s
   SQLite `roomApi` returns `registerDocs`'s `{ evict }`, which has no close. A session that wants
   the handle closed, as run 1's did, changes the function's return to the `Database`, and then
   the kept test no longer runs on the JSON file. That is the only half-point lost. Either
   `backends.md` / `recipe.md` (*Its test*) should show the close that leaves the test untouched,
   or the API should give both backends' `registerDocs` the same `close()`. The second would be an
   item for Peter. Pages: `recipe.md` (*Its test*, last paragraph), `backends.md`. The scenario line
   is right and agrees with the skill ("its test stay as they are").

2. **`ledger.md` reads as if the guard were per row, and it is per field.** "Each row is walked
   once by its net change" and "a single root is one row" sit beside "A field written since by
   anyone is a conflict". Run 2 took the row reading and told the user so, wrongly. In the scratch
   check, another field of the same row written since did not stop the walk. Add one plain line
   under *The walk*: the walk sets back only the fields its entry changed; another field of the
   same row, written since, does not stop it. Page: `ledger.md` (*The walk*). No scenario line asks
   for this; scenario 2 could gain one ("says truly what a walk refuses").

3. **`examples/kanban` contradicts the table rule.** Its `boardApi` runs
   `createTables(db, schema)` on `KANBAN_DB`, a file that can be kept. `SKILL.md` and `sqlite.md`
   now say that is only for a database thrown away, and `testing.md` cites kanban's `run.ts` as
   *Working*. Run 2 made that file database survive restarts and left `createTables` in place, so
   the copied app now breaks the rule the skill states. Either kanban is `:memory:` only, or its
   tables come from a migration. Since an example is the skill's worked answer, this is an item for
   Peter. Pages: `sqlite.md` (Gotchas, first line) is right; the example is not.

4. **The cursor's keeping (minor).** `ledger.md` says to treat a chosen `clientId` as a secret, and
   `SKILL.md` says tokens never go in the socket URL, but `connectWs` puts `clientId` in the URL's
   query (`src/client/client.ts:297`). Run 2 also kept it in `sessionStorage`, which a duplicated
   tab copies. One line in `ledger.md` (*The cursor*) on where a page keeps it would help. The URL
   is an API matter for Peter. Page: `ledger.md`.

5. **The new pieces go unexercised.** No scenario asks for `accept`, `ownership.md`'s who may
   write and the group some people are outside of, or `default: "now"`. Run 3 used `timestamptz`
   and wrote ISO times with a zone, which is the only time rule touched this round. A scenario
   would test them: for example, a notice board only admins post to, each notice timed by the
   server. Pages: `ownership.md`, `schema.md` (*A document's own rule*, the `now` default).

6. **Harness (minor).** Each project's `package.json` and `bun.lock` still name
   `file:/Users/peterb/Workshop/blueshed/dzql/packages/...`, though `node_modules` holds the packed
   contents. A session that ran `bun install` or `bun add` would resolve against the live checkout
   again, which was round 2's trap. None did this round. Pin the `.packed/*.tgz` instead. Page: none
   of the skill's; `scripts/evals.ts`.
