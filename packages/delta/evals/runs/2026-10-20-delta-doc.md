## Findings

1. **The skill still contradicts itself on how SQLite's tables are made, and both runs that made
   tables took the migrations side again.** `SKILL.md` ("Its tables are made by its migrations")
   and `migrations.md` ("a history from empty is the way for a new app") point to `migrate` plus
   `delta migrations make`. `recipe.md`'s "Moving to SQLite" paragraph, `backends.md`'s block,
   `sqlite.md`'s example and first gotcha, `testing.md` and `local.md` show `createTables` and
   never mention migrations. Runs 1 and 3 ran `delta migrations make` and `migrate`, and lost half a
   point each on scenario lines 1.3 and 3.7, which ask for `createTables`. The scenario lines
   contradict `SKILL.md`; either they should accept "`migrate` before `registerDocs`", or
   `backends.md` / `sqlite.md` should say once that an app makes its tables with `migrate` and
   `createTables` is for tests, scripts and in-memory seeds. Pages: `SKILL.md` (Invariants),
   `recipe.md` (last paragraph), `backends.md`, `sqlite.md`. (Round 1 finding 1: still holds,
   unchanged.)

2. **Harness: a copied example must stand on its own.** `examples/kanban/tsconfig.json` extends
   `../../tsconfig.json`, so copied out of the repository it reads a file that is not there and
   `bun check` fails before the session starts. This is what failed scenario 2's check, not the
   session. Either the harness writes a standalone `tsconfig.json` after a `copy` (the one runs 1
   and 3 wrote: `jsx`, `jsxImportSource`, `strict`, `moduleResolution: "bundler"`,
   `types: ["bun"]`, `noEmit`), or the examples carry a self-contained one, which would also serve a
   person who copies an example out. Likewise, kanban's tests stay in delta's `tests/`, so a copied
   example has no `bun test` to run; a scenario that copies an example could copy its test too.
   Pages: none of the skill's; `examples/kanban/tsconfig.json` and `scripts/evals.ts` (`copy`). (New;
   it is the price of round 1 finding 6's fix.)

3. **`recipe.md`'s `tsconfig.json` block still lacks `"types": ["bun"]`.** It did not bite this
   round: runs 1 and 3 wrote a fuller tsconfig of their own and pass `bun check`; run 2 never wrote
   one. The block and `tests/recipe.test.ts` (which never type-checks it) are unchanged. Page:
   `recipe.md` (`### tsconfig.json`). (Round 1 finding 2: still holds as a page defect.)

4. **Nothing asks an app for a test.** This round, runs 1 and 3 kept one (two clients on a real
   server, `testing.md`'s pattern); run 2 tested with a throwaway script and kept nothing. The recipe
   still ends with delta's own test, not the app's. Pages: `recipe.md`, `testing.md`; for undo,
   `ledger.md` could point at a kept two-cursor test as its "Working" line does at `examples/lists`.
   (Round 1 finding 3: still holds.)

5. **The `file:` install nests a second railroad, and it breaks the page.** Each project has
   `node_modules/@blueshed/delta/node_modules/@blueshed/railroad`. Run 1 reports that with two copies
   the page did not update in Chrome, and moved the nested copy out of the project's `node_modules`
   to make it work. Runs 2 and 3 still have it, so their pages may not update in a browser either
   (not checked in a browser here; their tests drive the client from Bun and pass). The install is
   also a tree of symlinks into the checkout, so delta's `tests/`, `examples/` and `evals/` are in
   every project. This is a harness issue, not a skill miss, but any browser-level line could fail
   for it. `testing.md` already says never `file:` or `bun link`. (Round 1 finding 4: still holds,
   now with a concrete failure.)

6. **A reset seed and the ledger (minor).** Run 2 emptied `delta_ledger` and `delta_versions` by hand
   because kanban deletes and reseeds its board at each start. Nothing in the skill says how to start
   a ledgered database afresh, and `migrations.md` warns against writing delta's own tables. One
   gotcha line in `ledger.md` (a reseeded database is a fresh database: delete the file, or use
   `:memory:`) would answer it. Page: `ledger.md` (Gotchas).

7. **Scenario 1's line 5 cannot fail.** "installs @blueshed/railroad beside delta" is decided by the
   harness, which puts railroad in every delta start's `package.json`. Drop the clause, or start the
   scenario empty. (Noted in round 1's table; still so.)
