## Findings

1. **A value a rule sets as the row is written is worked out instead (delta-doc
   `reference/schema.md:58-61`; evolve `references/sqlite.md:276`, `references/migrations.md`).**
   "A fact that comes from other rows is worked out, never stored", and its limit, "a value a
   person may change, or one from a rule that may change, is the row's own and is stored", sit at
   the end of a bullet about other rows. Two weeks from the loan's own day is not from other rows,
   and the session read the limit as a case for later: "If a loan can be extended, or the loan
   period changes ... `due` becomes a column" (todo 12). Run 5 passed this with the Shed's own
   words in the page (its finding 6); without them the limit does not reach. Say it where a column
   is declared: a date or amount a rule gives at the write is stored, set by the server, and a
   migration fills the rows before. And the API has no place for the server to set it: a
   `default` is "now" or a constant, so the page would compute `due` and send it, as in run 5. An
   item for Peter: a column the server fills from the row as it is written.
2. **The list stayed a JSON file while SQLite named its rows (evolve `references/auth.md:3`,
   `references/sqlite.md:275`, `references/two-documents.md:172`).** Sign-in put the people in
   SQLite at stage 2, their picks and loans under them, each naming a tool in `tools.json`; the
   list stayed there until stage 5. `sqlite.md:275` forbids it ("No document stays a JSON file
   while one on SQLite names its rows"), but no session read `sqlite.md`: `auth.md` says people
   are kept in SQLite and links it for the order, and `two-documents.md:172` says the kitchen and
   undo "need no move to SQLite". So the loans could not be in one transaction with the list, the
   kit's parts had no migration (todo 11), and "a tool out stays on the list" was a closure over
   another database. `auth.md` should say what moves with the people. (`expected.md` stage 3 still
   asks for every document in SQLite; `two-documents.md` now teaches otherwise: one is stale.)
3. **Who may write a list everyone reads: the API says it, and the session waited (delta-doc
   `reference/ownership.md:25-32`; evolve `references/auth.md`).** With `accept` told who, the
   keeper's list is one line, and the session wrote todo 1 at stage 1, renewed it at stages 2 and
   5, and never wrote the line: it read "Sam adds" as a person in a story, not as a rule. At stage 5
   a visitor writes the list and the message (the probe). The pages should say a story that names
   who does a thing says who may: the rule is written with the story, not kept for one.
4. **A time only the server sets takes the client's (delta-doc `reference/schema.md:94-108`;
   delta `src/schema.ts:26`).** `default: "now"` fills a time left out; one sent is stored unless
   each document writes the rule (the page's is a test over `op.path` and `op.value`), and this
   app's `basket:` has none: a member's `since` of 2020 was stored. The name says the server sets
   it, and the server takes any. Where an example only looks right because a rule dodges a trap
   in the API, the API changes: an item for Peter, `default: "now"` refusing a sent value by
   itself, on every backend.
5. **`openStore` and the visitor (dzql `src/postgres/app-store.ts`; evolve
   `references/postgres.md`).** The link gate refuses a socket with no session, so on the store a
   list everyone may read, `shared: true`, is not open to someone not signed in. The app wraps the
   gate to make them a person with no row (`store.ts:90-93`), which made `owns: "AUTHENTICATED"`
   admit them, so `people:` is owned by a function (`people-api.ts:66`, `signedIn`). Besides it,
   two servers opening one new database at once fail on the compile (dzql locks its migrations,
   not `applySql`; `store.ts:77`), the old links and sessions move by INSERT, and a command writes
   by `delta_apply` as the owner (`link.ts:21`). Items for Peter in dzql: a shared document open
   without a session, the open taking its own lock, and a command's write through the store.
6. **A rule over other rows has no home (delta-doc `reference/schema.md:75-92`).** `accept` is
   synchronous and sees the op alone, so "a tool out stays on the list" went to a socket handler in
   front of the store (`store.ts:124-128`), which holds for the page's socket and not for every
   writer, the trap `schema.md:91` names. It is a reference: a loan names a tool, and a tool named
   by a loan is not removed. If the list and the loans share a database (finding 2) and the schema
   can say a column names a row, the database refuses it. An item for Peter: a reference the schema
   declares, or a rule that may read.
7. **Fewer tests, faster (the template's `tests/`; evolve `references/testing.md`).** 51 tests over
   the template's 35 against run 5's 63, in 22 fewer minutes; every story is told and coverage is

8. **A session reads the checkout through its links (`create-blueshed --local`; `driver/run.ts`).**
