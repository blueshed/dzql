## Run 4's four findings, settled or not

1. **A due date worked out in the page: settled.** The due date is a column, `loans.due`
   (`src/resources/borrowing/borrowing-api.ts:45`), written with the borrow, and a migration of its
   own fills it for the loans before from each loan's day (`borrowing/migrations/004-due.ts`). What
   is left: the page works it out from the phone's clock and sends it (`borrowing.ts:61-64`), and
   the server takes any `due`, as it takes any `borrowed` or `returned` (the app's todo 4; finding 8).
2. **The tools staying JSON, or a JSON-in-Postgres store: settled, a stage late.** The list stayed
   in `shed.json` through stage 3 (its lines named tools in another store, todo 5), and moved to
   SQLite at stage 4, the session citing the evolve skill: "rows that one document names in another
   are in one database" (`shed-api.ts` at d4c75e1). At stage 5 every row is in Postgres, made by
   the histories and the compiler; there is no `kept_docs` and nothing calls delta's internals to
   write. One document stayed JSON: the message, kept per shed (finding 9).
3. **A group with people outside it, owned by a function: not settled**, though `ownership.md` now
   names this very case. A field is a text column on `people` (`people-api.ts:36`), and a field's
   loans are a recompute document owned by a function (`borrowing-api.ts:83-86`). The session read
   the membership shape and declined it, saying why in todo 11 (finding 1).
4. **Python writing `todo.jsonl`: not settled.** Stage 3 did it again and said so: "I wrote
   `todo.jsonl` with a Python script in the shell rather than the file tools, which goes against

## Findings

1. **A group with people outside it is still a function, and the trap beside it is in the API
   (delta-doc `reference/ownership.md`, `reference/scope.md`; evolve `references/postgres.md`).**
   The page's shape puts "what the field has" under the field, through a membership. Here a loan
   is a member's own first (`member:` roots at the person) and the field's second, and two people
   have no plot; moving loans under a plot breaks `member:`. The other way the session tried, a
   list over people scoped by field with loans included, would send every loan, Dot's included:
   a list's includes load in full (`scope.md`), whatever the scope admits. It saw that and wrote
   the function. That is a document that looks right and is not: an item for Peter, either a list's
   includes following the roots its scope admits, or a path a document can take through a
   membership to rows that hang under the person.
2. **A rule the schema cannot say has no home (delta-doc `reference/schema.md`, "Validating before
   a write"; evolve `references/document.md`).** `accept` went with `registerDoc` on 20 October
   (bb48256f) and nothing took its place, so "a tool needs a name" became a socket handler ahead of
   delta, for all five stages (todo 1): it holds for the page's socket, not for `createLocal`, the
   CLI or the thin client. An item for Peter: a document's own rule, on every backend.
3. **Who may write a list everyone reads (delta-doc `reference/ownership.md`).** `owns` says who
   may open a document; nothing says who may write it. At stage 5, `shed:` is on a listener of its
   own with no auth, and a socket nobody signed in to added a tool and was answered with it (a
   probe in a copy of the app). Before stage 5 any signed-in member could; todo 2 has carried it
   since stage 1. The page needs the shape (everyone reads, the keeper writes), or the API does.
4. **A hand `up` across backends (evolve `references/migrations.md`, `references/postgres.md`,
   "The history moves with the app"; delta-doc `reference/migrations.md`).** An `up` is the
   backend's SQL, and a migration that has run is never edited; but a history written on SQLite
   runs on Postgres too, from its first migration. The session edited `002-picks-returned.ts` and
   `004-due.ts` to hold both dialects, and said it broke the rule. The pages should say what to do:
   a new database takes the rows already migrated, or an `up` is written once for both.
5. **`openStore` is too narrow for an app with sign-in (evolve `references/postgres.md`; dzql).**
   The page teaches `openStore`, which takes one history, no `auth` and no custom documents. This
   app has three histories, sign-in, `out:` and `field:`, so it wired dzql's parts by hand
   (`store.ts`, 109 lines, two listeners) and raised `dzql.definer`, which dzql does not export, to
   read who is signed in and what is out (`owned.ts`, todo 14). Smaller than run 4's 94-line
   writer over delta's internals, the same kind.
6. **The held-out example leaks into the skills (delta-doc `reference/ownership.md:34`,
   `reference/schema.md:57`, `reference/cli.md:29`).** "A field's plotholders; the keeper is in
   none", "a due date someone extends" and a role of `keeper` are the Shed's nouns, which run 3
   took out of every page. Runs from here are less held out than 3 and 4: read the settled finding
   1 with that in mind. Say the shapes in another example's nouns.
7. **Python for `todo.jsonl` again (the template's `CLAUDE.md`).** The rule says to write the pair
   with the file tools; the session knew and did otherwise. The template could say why (the
   lineage is Bun only, and a ledger line is edited in place with Edit).
8. **A time the server should set is the phone's (delta-doc `reference/schema.md`, the limit of
   "worked out, never stored").** "Set as the row is written" does not say by whom. `borrowed`,
   `returned` and now `due` come from the page's clock, and the server takes any value (todo 4,
   open since stage 2). With finding 2, there is no place for the server to set them.
9. **The message stays one shed's (evolve `references/postgres.md`: "a document still kept as a
   JSON file moves to SQLite first, then here").** The template's message is JSON, and at stage 5
   each shed kept its own (todo 13), so a save at the south gate does not reach the north: story 6
   holds for the Shed's own stories and not for `follows`. The step to Postgres could take the
   template's own documents with it.

Not friction: stages 1 to 5 each ended "nothing committed", which the driver does.
