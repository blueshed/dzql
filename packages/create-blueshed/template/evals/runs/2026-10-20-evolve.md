## Findings

1. **The app's CLAUDE.md sends a whole-app request to the model's page and tells the session to wait.** This is the root cause of scenarios 2 and 4. The "Where an app starts" paragraph of `template/CLAUDE.md` says an app starts with stories on the model's page, and to build "when the teller calls every story true". Scenario 2's query reads like the start of an app, so the session followed that paragraph and the `modelling` skill instead of evolve's Order of work. Evolve's Order of work says the opposite ("Write what the user asked into stories.ts" and build). Scenarios 1 and 3 are feature-sized and did not trigger it.
   - **Page:** `evolve/SKILL.md`, Order of work. It should say that a request to build is built now, its stories written into `stories.ts` directly. The model's page is for when the user asks to model, or is there to tell and confirm the stories. With no one to answer, decide and say what was decided (as scenario 2 itself did for "the kitchen cannot change an order").
   - The same fix is needed in `template/CLAUDE.md` "Where an app starts" (outside the skill, but it is what the session obeyed).
2. **http.md says files go in S3 but never says why, so the session reasoned its way to the volume.** The volume needs no credentials and the app already has one. Those are good reasons in a "start light" template, so the skill must either give a reason or accept the volume.
   - **Page:** `evolve/references/http.md`. It should say why a file is not kept on the volume. For example: one server's disk; the bytes served by the bucket, not the app; the volume is for documents. It should also say that `startServer({ s3 })` is the seam the tests use. If the volume is acceptable for the light client, then scenario 3's lines are what is wrong.
3. **Remove was not done in scenario 1.** document.md's example has add and remove, but the query only asked for add, and the session followed the query and logged the rest.
   - **Page:** `evolve/references/document.md`, if remove should come by default (say "a list people add to, they can take from"). Otherwise the scenario line is what should change (see below).
4. **A real dzql bug, found by scenario 2 and confirmed here.** `modelIn` in `packages/dzql/src/cli/model.ts` reads `tables.stories` and `tables.documents` whole, including closed versions (`valid_to` set). In scenario 2's `model.json`, 12 of the 15 document rows are closed versions. `bunx dzql model check` there reports `menu`, `order` and `kitchen` two or three times each as unheld and empty, so `model/` is never made. This is not an evolve page, but it blocks anyone who follows the modelling path. It is logged in that app's `todo.jsonl` #1, not in dzql's.
5. **Harness: scenario 4 depends on scenario 2 succeeding.** With `after: 2`, a stop in 2 means 0 in 4, and 4 tells us nothing about migrations.md. The harness already uses fixtures for scenarios that name an app; scenario 4 should have one: the order app as sqlite.md leaves it, with a `data/app.db` holding repeated lines.
6. **Harness: parallel evals share ports and leave servers running.** Scenario 2 found :3001 taken by `dzql-modelling-2` and left `dzql model` running on :3002 after it ended. The harness should give each run its own port range, or kill `.server.pid` and model pages when a session exits.

### Where a scenario line is wrong or out of date with today's skill

- **Scenario 2, line 2** ("Keeps them in SQLite ... because the kitchen and every order share rows") contradicts `SKILL.md` and `sqlite.md`. Both say the JSON file holds documents over the same rows, undo and history: sqlite.md adds the kitchen "as they would be on the JSON file". SQLite is only for a file too big to rewrite, or a schema changing on data in use. The line should accept the JSON file (`registerDocs(..., { ledger: true })` from `@blueshed/delta/json`) and not ask for SQLite until scenario 4. Even so, the skill's only worked kitchen-and-undo example is in sqlite.md, which pulls the other way. A short JSON-file kitchen and undo in two-documents.md would make the skill agree with itself.
- **Scenario 2** has no line for today's additions:
  - Undo and Redo pressed on the page (`bento({ undo, redo })`)
  - the cook's cell for the kitchen
  - tests through `tests/documents.ts` (`documentsOf`)

  It should ask for the Undo control and a browser test that presses it, as sqlite.md does.
- **Scenario 1, line 2** "puts the view in a route in src/app.tsx" is out of date. The page is a bento now: the view is a cell in `cells` (and a modal in `modalOf` for new or remove). It should say "a cell in `cells`".
- **Scenario 1, line 4** "Renders the list with `list()`" is out of date. document.md says "A list is `rowsOf`, keyed by id". The line should name `rowsOf`.
- **Scenario 1, line 3** "removes by id" asks for more than the query does ("type a note, press Add"). Either add removing to the query, or make the line "a remove, if one is added, is by id".
- **Scenario 4** has no line for today's thin-client step, and does not need one. But "Leaves the page and its documents as they were" should also name the Undo and kitchen tests, which migrations.md says still pass.
