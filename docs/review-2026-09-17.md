# Review: is eta DRY, KISS and YAGNI?

*17 September 2026. Asked for by Peter: a deep review from first principles, no code, against two
questions -- does eta deliver what its README promises and has it been over-engineered; and is it
using Bun to best effect. Written by Claude (Fable 5.1) from six read-only passes (kernel server,
kernel client, the wedding, the ticker, the docs against the code, the use of Bun) plus my own
reading and measurements. The working tree at the time held uncommitted work from the same day:
the bento surfaces moved into the kernel, and chat rebuilt from its reclaimed stories.*

**How far to trust it.** Nothing here was run; it is all from reading code. Findings marked
**[checked]** I re-read in the code myself after a pass reported them. Everything else is a pass's
finding that I did not re-check, and says so. Line numbers are as of this date.

## The short answer

- **The core is good and small.** About 400 lines deliver the README's three ideas, and every pass
  independently put the same parts on its leave-alone list.
- **Everything of substance that is wrong is outside those three ideas**, in four layers added since:
  render-delivery optimisation, UI state kept as server documents, bento used as features, and the
  documentation.
- **DRY: code C+, docs F. KISS: C-. YAGNI: D** by the project's own rule.
- **The safety net has holes**: the stories check the tables, not what anyone was sent; chrome
  stories cannot fail; real bugs sit under 100% coverage.
- **Bun: B+.** The runtime is used well and no layer exists because a Bun feature was missed. The
  misses are configuration. The platform that is under-used is the browser.

## Does eta deliver what the README promises?

The README promises three things: documents with patches and a ledger; the server as the only
renderer, with a morph on the client; applets. The core that delivers them:

- the ledger's undo/redo cursor (`src/ledger.ts`), no state outside the ledger
- the ~30-line generic dispatcher (`src/server.ts`), no per-feature branches
- the ~90-line morph (`src/client/morph.ts`)
- the applet boundary and registry
- the document `patch()`/inverse/one-transaction pattern
- the ticker's feed; the wedding's domain tables, triggers and figures

| README promise | Verdict |
|---|---|
| Legible wire | True. During this session I joined a chat room, watched it and replied from a terminal with no browser. |
| Zero infrastructure | True: one process, one SQLite file, no build step. |
| Almost no client | True. Measured 2,649 B gzipped for the kernel client (README says 2.3 KB); the wedding's is 9.1 KB (README says 8). |
| Undo and redo for free | Mostly. Chat's reclaimed stories found two undo faults the same day (both fixed in the working tree). |
| Measured, not claimed | Stale. Story counts are given as 6/13/51; they are 10/23/63. The chat byte tables describe a page that no longer exists. |
| "Each example needed nothing in `src/` it did not already have" | False. `change-request.md` lists 11 kernel changes the wedding asked for; bento added K1-K3; the bento surfaces were added to `src/` on the day of this review. |

Sizes, non-test lines: kernel 2,528 (server 1,228, client 536, bento/tray/icons/html 764); chat 673;
ticker 1,240; wedding 4,111. Docs: about 33,500 words -- more prose than the kernel has code.

## Has it been over-engineered? The four layers

### 1. The layer that optimises how renders are delivered

Three render tiers, the `#c-<docType>` wrapper, `fragments`, fragment add/remove ops, three
byte-measuring scripts.

- No example has two compartments rendering at once (chat: one; ticker: only `ticker` has a
  `render`; wedding: `household` and `board` are exclusive by role), so the wrapper and the middle
  tier send what the full page would, through a lesser client path (`applyFragments` skips the URL
  sync, `data-moving` and `data-reveal`).
- The wedding spends ~170 lines (`compartments/household.ts:124-194` and the exports kept for it),
  and a third copy of its page routing, to save ~10 KB per colour tap at a wedding's traffic.
- The Cost section is 40% of the README; those numbers bought most of this complexity.
- **[checked] It produced real bugs in the ticker.** Compartments without a `render` cannot use the
  kernel's default, so each hand-lists which page elements a write touches, and that list must be
  right for every combination of tray state. It is not:
  - `ticker/compartments/ticker.ts:74-81`: a price tick with a symbol's drawer open redraws the rows
    and not the drawer, so the drawer's price goes stale.
  - `ticker/compartments/watchlist.ts:51-60`: pressing Watch from a market row's drawer updates the
    board count and the board applet; the drawer still says "Watch" / "Watched: no" and the row
    gains no "watching" note. `server.test.ts:224-227` receives that render and asserts nothing.

### 2. UI state kept as server documents (the tray)

- 10 of the wedding session's 12 writable fields are UI state; four mutually exclusive drawer fields
  (`focus`, `gift`, `keep`, `answering`) and two modal fields are modelled as independent optionals.
  The ticker's desk has seven fields.
- Every find keystroke is a websocket write, a SQLite upsert, a full-page render and a morph, over
  lists of 2 to 16 rows.
- Domain writes reach into the tray's document to close modals (`closeAsked`, in the wedding twice
  and the ticker once), bypassing the tray's own permit and echo.
- All three examples grew an `at()` mini-grammar to place the cast in tray state; `docs/stories.md` says
  "it will not need a grammar".
- How it happened: "no client-side domain state" was applied to *view* state as well.
- The simpler reading: a page and its open drawer are one address (`guests/2`, `gifts/1`, `answer`,
  `guests/new`), which belongs in the URL the wedding already has -- and gives the back button and
  shareable links for free. `Ui` becomes `{page}` plus find's collections.

### 3. Bento used as features, not as a way of looking

Chat had this until the day of this review. Still present:

- **Ticker.** 0.42.0 added 10 stories, no new intent (the three human writes and the tick are
  unchanged) and ~250 lines. Dropping a symbol went from one tap to five gestures and four desk
  round-trips, ending in a confirm modal whose own text says "Undo brings it back". The list reading
  exists because the SVG board has no tappable rows: a workaround, not a second reading.
- **Wedding.** A household's own guest list (2-5 rows) has a search box, a tally and a hide-misses
  eye. Its own comment (`views/board.ts:344`) says find is for "the one list long enough to need it";
  it is on four.

### 4. Documentation

- ~33,500 words for a ~2,300-line kernel. A builder must read 8,400 words before adding a feature,
  ~20,000 to decode the citations.
- Each core rule is restated in 4-11 places (the tray having no `render`: 11), so a fix never
  reaches all of them. **[checked]** "The ticker has no tray" survives in `CLAUDE.md`, the skill,
  its reference and `src/example.ts`; `examples/ticker/index.ts:14` says `tray: desk`.
- The eta-app skill bans a `views/` layer; the ban shipped in the same commit (`d9d28dd`) as the
  wedding's 1,170-line `views/`, which `CLAUDE.md` and the reference then cite as the exemplar.
- "Compartment" means two things inside `src/` (the document handler in
  `compartments/compartment.ts`, the grid cell in `tray.ts`); "tray" means three (the session
  document, the grid layout function, a docType string).
- ~200 code and doc comments cite finished work orders ("item 10's rule 3", "K3") instead of stating
  the current rule (112 in non-test code, 49 of them in the kernel). `change-request.md` and
  `bento-request.md` (8,200 words) are kept alive only by those citations, and
  `bento-request.md:230-246` still specifies the three-compartment chat.
- Docs cite things that do not exist: chat's `room-picker.ts` (seven code comments still do too);
  `echoAndNotify` quoted from chat's `room.ts`; a `Compartment.ledger?: false` flag designed inside a
  comment.
- **Process.** The skill's nine-step checklist starts at `db.ts` and never mentions stories. The only
  doc pressure that produces stories (`docs/stories.md:130-132`, `bento-request.md:30-32`) produces them
  after the feature, for tray state. The one stories-first instruction a builder auto-loads is a
  `CLAUDE.md` bullet added on the day of this review.

## DRY, KISS, YAGNI

### DRY: code C+, docs F

- The largest code duplicate -- the bento box-page code, its CSS and the find/reading/eye state in
  three examples -- is merged into the kernel in the uncommitted work (`src/bento.ts`,
  `src/bento.css`, `src/html.ts`).
- Remaining: "tell the audience about a write" spelled four ways (`notify()` at 7 sites; an identical
  hand-rolled echo in `wedding/board.ts:38-43` and `household.ts:41-46`; an identical tray echo in
  all three session/desk compartments; chat's `notifyPresence`); `replay` a near-copy of `write` in
  all six implementations; the wedding's 21 permit regexes restating what `applyOne` already refuses;
  the `waitFor` test helper copied four times; small repeats in the ticker (`cityOf` x3, `Quote` x2,
  the tick-path regex three ways) and the kernel (the ledger row type x3, the undo/redo wire shape
  x4, `Inspection` x2, two argv loops).
- Docs: see layer 4.

### KISS: C-

Concept count, not line count: three render tiers; two client render paths with unequal features;
five ways to trigger a write (submit, click, blur, change, input) with two commit paths; three
channels by which data reaches an applet; a ledger "compartment" whose own comment says it is a
tool; an event bus (`renderRequested`) with one listener, which forces a module-global `active` and
a monkey-patched `server.stop`; `Example.tray`, which `assemble` treats exactly like any other
compartment.

### YAGNI: D, by the project's own rule ("a page nobody's story sees is not a page")

- 28 of 96 stories are chrome (wedding 18, ticker 10): tray state, not a person's intent. All 12
  wedding stories added since 15 Sep are chrome and use the mock-up's cast, not the seed's.
- Wedding code with no story: `seq` reordering, picture upload (`/api/picture`, `picture-field.ts`,
  the `pictures` table), the confirm modal, the deadline lock, editing the couple's own names,
  `fragments`, `cli.ts`, unclaiming a gift as a `does`.
- The other way: three wedding intent stories have no gesture on any page (`stories.ts:105`, `:107`,
  `:108`), and the caterer's dish/drink/dietary totals (`documents/board.ts:61-90`) are computed and
  never shown. The harness cannot notice, because it sends `does` straight down the wire.
- Kernel features by number of users: `data-write-on="change"` 0; migration `legacy` adoption 0; an
  optional tray 0; multi-compartment pages 0; fragment add/remove 1; `sees` 1; the ledger's
  `undoable` column 1; `Applet.patch` 1 that needs it.
- From the day's own work: `choice` is used only by the wedding and `collectionPage` only by chat --
  a kernel helper with one caller is not shared; no example calls `crumbs` or `pageTools` directly.

## The safety net has holes

This explains how the rest went unnoticed.

- **[checked] The stories check the tables, not what anyone was sent.** `src/harness.ts:41-43`
  snapshots `renderFor(sessionId)`, a fresh in-process render. A passing `seen` means the database
  changed in a way a render shows; it does not mean the person's page was told. None of the delivery
  code -- audience, echo, fragments, tiers, morph -- is vouched for by any story. As far as the
  kernel pass could tell, deleting every `notify()` call would stay green.
- **[checked] `docs/stories.md` describes a harness that is not the one in `src/`.** No permit-rule
  coverage check ("permit" does not appear in `harness.ts` or `stories-run.ts`) and no Canon 2
  browser comparison. I repeated the permit-coverage claim to Peter as fact earlier the same day,
  having read the doc and not the code.
- **[checked] Chrome stories cannot fail.** Any tray write changes the author's own render, and they
  are off the ledger, so the undo leg is skipped. "Grace claims the kettle from its drawer; the
  couple see it claimed" (`wedding/stories.ts:71`) passes: the write only opens gift 2's drawer, the
  couple are not in `seen`, and there is no Grace and no kettle in the seed.
- **[checked] A click in a `data-write` field sends a blank write.** `src/client/app.ts:237-244`
  excludes only `FORM`. Clicking into the find box after typing sets the filter to `""` on the server
  while the box still shows the word; the wedding's blur-edit fields send a junk op per click.
  `src/client/app.test.ts:186-188` says so in a comment and focuses the field from script instead.
- **[checked] A household can give itself unlimited plus-ones.** The permit
  (`wedding/compartments/household.ts:103-107`) counts only guests with `named_by === "household"`;
  `addGuest` (`documents/household.ts:113-115`) takes `value.named_by` from the wire -- the shape
  that lets undo restore a guest -- so `{name, named_by: "couple"}` is never counted. `id`, `coming`
  and a look pass the same way.
- Not re-checked: a typed-in field keeps stale text after an undo (the morph has no `.value`
  handling) and the next blur silently re-sends it; a second tab on the same session goes stale on
  tray writes yet still receives fragments for a room it is not showing; the kernel draws
  `role="button"` divs with no keyboard handler anywhere in `src/client`; on disconnect the client
  morphs `#app` to a text string, destroying typed input and every applet's state.

## Are we using Bun to best effect? B+

Bun 1.4.2. Used well: `req.cookies`; `routes` with HTML imports (bundler, TypeScript, CSS and no
build step); `bun:sqlite` with prepared statements, `db.transaction` as the only write path, WAL;
nested transactions as savepoints (the harness's per-story rollback depends on it); typed `ws.data`
and auto-corked sends.

Would not change: websocket topics do not fit, because renders differ per viewer and who sees a
document is computed from the database at send time; `--hot` would leak the ticker's interval, the
database handle and the socket registry; `Bun.escapeHTML` cannot run in the browser, where the
wedding's applets import `esc`.

The misses are configuration:

- **[checked] No `bunfig.toml`, no `.env.test`.** A bare `bun test` writes to the dev `db.sqlite`,
  and "aim for 100%" is a convention. `.env.test` (`DB_PATH=:memory:`, `TICK_MS=0`) plus
  `[test] coverage = true`, `coverageThreshold = 1.0` make the bare command right and the aim a gate;
  the `CLAUDE.md` warning goes.
- `bun test --isolate` would delete ~23 lines in `src/server.ts` (the module-level `active`, the
  monkey-patched `stop`, the clearing path and its test) that exist only because test files share a
  process.
- **[checked] `bun run start` runs in development mode**, and `server.log` holds the one line
  `nohup: NODE_ENV=production: No such file or directory`. `src/pid.ts` can kill the wrong process:
  every dev script shares one pid file, `pid.test.ts` deletes the real one, and `disown` is not
  POSIX.
- **[checked] `Bun.WebView` is `@experimental`** (`bun-types/bun.d.ts:9432`), defaults to a
  macOS-only backend, and has 30 call sites; `@types/bun` is pinned to `latest`.
- Smaller: `util.parseArgs` for the two argv loops; route params for `/pictures/*` (the current
  `decodeURIComponent` throws on a malformed `%`); `new Database(path, { strict: true })`;
  `development: { console: true }`; `perMessageDeflate`.

**How the two questions relate.** Bun gives eta the bundler, SQLite, websockets and cookies for
nothing, which is why the core is 400 lines. The simplicity Bun gave was spent above it, on the four
layers; none of the over-engineering came from fighting the platform. The platform that is under-used
is the browser: the URL for page and drawer state, `<button>`, `<details>` (one guarded line in the
morph to keep `open`, and two wedding applets become server HTML), `datalist` (the ticker's
130-line city picker), the `change` event.

## Why it happened

Layers arrived as request lists (`change-request.md`, `bento-request.md`). Each finished item left
code, a doc section and comments citing it; each layer was tested against itself to 100% coverage;
nothing tested the whole against the README's promise. Builders -- Claude included, on the day of
this review -- satisfied the letter: a story for every feature, written after it; a rule restated
rather than checked; a bug worked around in a test rather than fixed. The stories idea is the right
corrective, but the harness implements half of Canon 1 and none of Canon 2.

## What I would do, in order

Proposals, not decisions.

1. Fix the three checked bugs: the click handler, the plus-one bypass (the document learns whether
   it is replaying; fresh writes keep only `name`), the ticker's stale drawer.
2. Make the harness tell the truth: rebuild each member's page from the messages they actually
   received and compare it with a fresh render -- Canon 2 without a browser -- with an `inspect`
   round-trip as the barrier instead of a 40 ms sleep. Then delete the chrome stories, fix the false
   one, and for the three stories with no button either add the button or drop the story.
3. One render function per example (`Example.render(sessionId)`), and the kernel owns echo-and-render
   after a write; `replay` becomes `write(ws, docId, ops, undoes?)`. Keep `fragments` only where a
   measurement earns it -- chat's one `<li>`, the ticker's "nothing" -- and delete the wedding's.
4. Move the tray's page and drawer state into the page address: one field, plus find.
5. Cut the docs to ~3,500 words in four files: stories as step 0 in the skill; rules restated in
   place instead of cited; the two request files retired; the README's numbers generated from the
   runs; one meaning per word (rename `src/tray.ts`'s `Compartment`).
6. `bunfig.toml`, `.env.test`, `--isolate`, a production `start`, no `pid.ts`.

The passes' estimates of what this removes, not totalled against the code: kernel ~200 lines and
roughly half its concepts; ticker 1,240 to ~600; wedding ~450 lines; docs ~30,000 words. All of it
outside the 400-line core.

## Loose ends noticed in passing

- `examples/londons/` is tracked and holds only a `stories.ts`; `ETA_EXAMPLE=londons` would fail.
- `examples/bento/README.md:1` is a stray table row above the title.
- Exports with no importer outside their own file: `RenderWrite`, `RenderRequest`, `InspectDoc`,
  `Assembled`, `Listener`, `Outcome`, `Report`, `Seen`, `Told`, `Cast`.
- `CLAUDE.md` says compartments talk only through bus events; `chat/room.ts` imports from
  `./session`, and three compartments patch the tray's document directly.
- The ticker's ledger gains two rows a second while anyone is connected, and nothing reads them back.
- The `design/` artboards were not regenerated after bento rule 2 was amended on the same day.
