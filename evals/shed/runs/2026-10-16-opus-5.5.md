## Stage by stage

1. **The shed's list.** Shared document from the start (`registerDoc`, `openDoc`), in the
   template's resource layout. Tools are rows addressed by id. A tool with no name is a 400 with
   "a tool needs a name". The browser tests use two windows. It ledgered on its own that anyone,
   not only Sam, can change the list.
2. **Borrowing.** Two documents on one page: the list, and the member's own `member:<id>`. A
   basket line is `{tool: id}`, and its name is drawn from the list, so a rename reaches it.
   Borrowing adds the loan, dated by the server, and empties the basket in one write. It is kept
   in the data folder. No browser storage.
3. **What is out.** It moved to delta's SQLite store, with five documents over shared rows
   (`tools`, `members`, `picks`, `lent`). Sam's board is one document over every loan, and holds
   only members' names (`columns`). Undo is delta's ledger. **Partly:** "out" is a column on the
   tool (`tools.out`, who has it), written in the same change as the loan, not derived from the
   open loans. See finding 1.
4. **Kits and due dates.** The schema declares the due date, and the kit's parts are rows under
   their tool. Two migrations in their own files fill both for the loans already made. A test
   starts from a database in the old shape, with loans in it. The running server upgraded the live
   database, and Ann's loans survived, due 30 October.
5. **Two sheds, each one's own.** dzql: `applyFramework`, `generateSql` at start,
   `createDocListener` with `docTypeFromDef` and `auth`. A Postgres server when `DATABASE_URL` is
   set, else PGlite. Two servers share it, behind an advisory lock at start. The SQLite data was
   carried across. Each document's `owns` decides who opens it:
   - `member:<id>` opens only for that member;
   - the board for Sam and the committee;
   - the committee's list for the committee;
   - `tools:` for anyone;
   - each field's loans as a custom document.

   The list no longer carries who has a tool. Shown in the browser: Ben returned the strimmer at
   the south gate (3021), and Ann's list at the north shed (3020) changed to "in". Ann cannot open
   the south field's loans. **Partly:** one hand-written SQL index (finding 3), and its own
   sign-in (finding 4).

## Findings

Each says where the change belongs: the session, a skill or reference, or a library.

1. **A fact from another parent's rows (delta).** A tool's list cannot include its open loans: a
   loan hangs from its member, and a row has one parent. So "out" (stage 3) and "due" (stage 4)
   are stored on the tool, written in the same change as the loan. The skills don't say how to
   show such a fact; delta has no way to derive one. A delta question, then an `evolve` reference.
2. **Migrations write schema by hand (delta).** Migrations run before the schema adds what it
   declares. So a migration that fills a new table or column has to create it itself (`002`
   creates `parts`; `001` uses `ALTER TABLE`). Ask whether delta's `migrate` should take the
   schema's additions first.
3. **No unique constraint in the schema (delta).** Two sheds must not lend one tool at once, so
   stage 5 adds `CREATE UNIQUE INDEX one_loan_per_tool ON lent (tool) WHERE returned IS NULL` by
   hand. delta's schema cannot declare it.
4. **Sign-in from scratch (evolve, the dzql reference).** Stage 5 wrote its own sign-in
   (`logins`, passwords from `SHED_PASSWORDS`) in place of dzql's `auth-jwt`. The `evolve`
   skill's dzql step does not say that `auth-jwt` is there.
5. **The app keeps no record of its stories (paintbrush).** The stories went to each session by
   prompt; nothing in the template or the `evolve` skill gives them a place. They survive only
   as test names, numbered per stage, so "1." names four different stories.
6. **`owns` as a path (dzql step 3, not built).** The field's loans are a custom document, and
   `owns` is a function, as `expected.md` allows until step 3 ships.
7. **A gap in the stories.** No story says who may see who has a tool on the list. Peter noticed
   on stage 4: Sam sees it only on his board. To settle before the next run.
